4.1 Diseño y optimización de esquemas de bases de datos

Un buen esquema es la base de un sistema de datos confiable, eficiente y mantenible. El diseño deficiente genera redundancia, inconsistencias, consultas lentas y dificultades para evolucionar el sistema.

1. Modelo entidad-relación (ER)

El modelo ER describe el dominio en términos de entidades (cosas del mundo real), atributos (propiedades) y relaciones (asociaciones entre entidades).

Cardinalidades

Tipo Ejemplo Implementación típica
1:1 Empleado – Cuenta de usuario FK en una de las tablas (o fusión)
1:N Cliente – Pedidos FK en el lado N
N:M Estudiantes – Cursos Tabla intermedia (bridge / junction)

2. Normalización

La normalización reduce la redundancia y previene anomalías de inserción, actualización y borrado.

Primera forma normal (1FN)

  • Cada celda contiene un valor atómico (no listas ni conjuntos).
  • No hay grupos repetitivos.
-- MAL (no atómico)
cliente_id | telefonos
1          | 555-1111, 555-2222

-- BIEN
cliente_id | telefono
1          | 555-1111
1          | 555-2222

Segunda forma normal (2FN)

  • Está en 1FN.
  • Todo atributo no clave depende de la clave completa (no solo de parte de una clave compuesta).

Tercera forma normal (3FN)

  • Está en 2FN.
  • No hay dependencias transitivas: ningún atributo no clave depende de otro atributo no clave.
-- Problema 3FN: ciudad determina región
pedido_id | cliente | ciudad | region
1         | Ana     | GDL    | Occidente

-- Solución: separar ciudades
-- ciudades(ciudad PK, region)
-- pedidos(pedido_id, cliente, ciudad FK)

BCNF (Boyce-Codd)

Toda dependencia funcional relevante tiene como determinante una superclave. Es una versión más estricta de 3FN, útil cuando hay varias claves candidatas.

⚠️ Desnormalización consciente En analítica y data warehouses a menudo se desnormaliza (esquemas estrella o copo de nieve) para acelerar consultas de lectura. La clave es hacerlo de forma deliberada y documentada, no por descuido.

3. Claves e integridad

CREATE TABLE clientes (
    cliente_id   SERIAL PRIMARY KEY,
    email        VARCHAR(255) NOT NULL UNIQUE,
    nombre       VARCHAR(120) NOT NULL,
    creado_en    TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE pedidos (
    pedido_id    SERIAL PRIMARY KEY,
    cliente_id   INTEGER NOT NULL
                 REFERENCES clientes(cliente_id)
                 ON DELETE RESTRICT ON UPDATE CASCADE,
    fecha        DATE NOT NULL,
    total        NUMERIC(12,2) CHECK (total >= 0)
);

Tipos de integridad

  • De entidad: cada fila se identifica de forma única (PK).
  • Referencial: las FK apuntan a claves existentes (o NULL si se permite).
  • De dominio: tipos, CHECK, NOT NULL, rangos válidos.

4. Índices

Los índices aceleran búsquedas y joins, pero ralentizan escrituras y ocupan espacio. Indexa columnas usadas en WHERE, JOIN y ORDER BY de consultas frecuentes. 

-- Índice simple
CREATE INDEX idx_pedidos_fecha ON pedidos(fecha);

-- Índice compuesto (orden importa)
CREATE INDEX idx_pedidos_cliente_fecha
    ON pedidos(cliente_id, fecha);

-- Índice único
CREATE UNIQUE INDEX idx_clientes_email ON clientes(email);

-- Índice parcial (PostgreSQL)
CREATE INDEX idx_pedidos_activos
    ON pedidos(fecha)
    WHERE total > 0;
📌 Regla práctica No indexar todo. Mide con EXPLAIN ANALYZE antes y después. Un índice inútil solo añade costo de mantenimiento.

5. Optimización de esquemas

  • Tipos de datos adecuados (no uses VARCHAR(255) para un código de 3 letras).
  • Evita columnas calculadas redundantes salvo que el coste de cálculo sea alto.
  • Particionamiento por rango/lista en tablas muy grandes (PostgreSQL).
  • Separar datos calientes (transaccionales) de datos históricos (archivo / warehouse).
  • Documentar el modelo (diccionario de datos, diagramas ER actualizados).

6. Ejemplo de esquema completo (tienda)

CREATE TABLE categorias (
    categoria_id SERIAL PRIMARY KEY,
    nombre       VARCHAR(80) NOT NULL UNIQUE
);

CREATE TABLE productos (
    producto_id  SERIAL PRIMARY KEY,
    categoria_id INTEGER REFERENCES categorias(categoria_id),
    nombre       VARCHAR(150) NOT NULL,
    precio       NUMERIC(10,2) NOT NULL CHECK (precio >= 0),
    stock        INTEGER NOT NULL DEFAULT 0 CHECK (stock >= 0)
);

CREATE TABLE clientes (
    cliente_id SERIAL PRIMARY KEY,
    nombre     VARCHAR(120) NOT NULL,
    email      VARCHAR(255) UNIQUE,
    ciudad     VARCHAR(80)
);

CREATE TABLE pedidos (
    pedido_id  SERIAL PRIMARY KEY,
    cliente_id INTEGER NOT NULL REFERENCES clientes(cliente_id),
    fecha      DATE NOT NULL DEFAULT CURRENT_DATE,
    estado     VARCHAR(20) NOT NULL DEFAULT 'pendiente'
);

CREATE TABLE detalle_pedido (
    pedido_id   INTEGER REFERENCES pedidos(pedido_id) ON DELETE CASCADE,
    producto_id INTEGER REFERENCES productos(producto_id),
    cantidad    INTEGER NOT NULL CHECK (cantidad > 0),
    precio_unit NUMERIC(10,2) NOT NULL,
    PRIMARY KEY (pedido_id, producto_id)
);
